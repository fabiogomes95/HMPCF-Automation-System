## 1. Remoção da coluna `nmres`

### Problema

A coluna `nmres` foi criada pelos scripts legados para armazenar naturalidade (ex: "NATAL - RN"), mas estava sendo usada incorretamente como flag de data de nascimento inválida no novo script de migração. O campo `naturalidade` já existia separadamente para esse fim.

### O que foi feito

- `ALTER TABLE pacientes DROP COLUMN nmres` no PostgreSQL
- Removida de todos os scripts: `migrate_legacy_to_postgres.py`, `migrate_to_postgres.py`, `migrate_v2.py`, `recreate_pacientes.py`
- Removida de `backend/app/models/paciente.py` e `backend/app/schemas/paciente.py`
- Função `fix_nacionalidade` (que lia `nmres`) removida do `migrate_v2.py`

## 2. Remoção dos valores padrão falsos

### Problema

Os scripts legados inseriam "PRINCIPAL", "S/N" e "CENTRO" como defaults nos campos de endereço quando o paciente não tinha dado real. Esses valores poluíam o banco e apareciam na tela da recepção.

### O que foi feito

- `ALTER TABLE pacientes ALTER COLUMN logpcn DROP DEFAULT` (e NOT NULL)
- Mesmo para `numpcn` e `bairro_pcnte`
- `UPDATE pacientes SET logpcn = NULL WHERE logpcn = 'PRINCIPAL'` → 14.941 linhas
- `UPDATE pacientes SET numpcn = NULL WHERE numpcn = 'S/N'` → 15.012 linhas
- `UPDATE pacientes SET bairro_pcnte = NULL WHERE bairro_pcnte = 'CENTRO'` → 16.621 linhas
- Model, schemas e todos os scripts de migração atualizados para `None` em vez dos defaults

## 3. Validações obrigatórias de cadastro

### Regras implementadas

| Campo | Regra |
|---|---|
| `nome` | Obrigatório, mínimo 3 caracteres |
| `num_cpf` | Validação matemática oficial (dígitos verificadores + bloqueia sequências) |
| `cns` | Validação matemática oficial (mod 11, começa com 1/2/7/8/9) |
| `sexo` | Apenas `M` ou `F` — qualquer outro valor é rejeitado |
| `dtnasc` | **Obrigatória**, formato YYYYMMDD, data real, não futura, não > 130 anos |
| CPF ou CNS | Pelo menos um deve estar presente e matematicamente válido |

### Backend — `backend/app/schemas/paciente.py`

Adicionadas funções puras de validação:

```python
def _validar_cpf(cpf: str) -> bool: ...   # dígitos verificadores
def _validar_cns(cns: str) -> bool: ...   # mod 11
def _validar_dtnasc(dtnasc: str) -> bool: ...  # data real, não futura, <= 130a
```

Validators Pydantic em `PacienteCreate`:
- `@field_validator("num_cpf")` → chama `_validar_cpf`
- `@field_validator("cns")` → chama `_validar_cns`
- `@field_validator("nome")` → min 3 chars, uppercase
- `@field_validator("sexo")` → só `M` ou `F`
- `@field_validator("dtnasc")` → chama `_validar_dtnasc`
- `@model_validator` → garante nome + sexo + dtnasc + (cpf ou cns) presentes

### Backend — `backend/app/main.py`

Adicionado handler para `RequestValidationError` do Pydantic:

```python
@app.exception_handler(RequestValidationError)
async def _pydantic_validation(request, exc):
    # Extrai primeira mensagem de erro e remove prefixo "Value error, "
    # Retorna: {"detail": "CPF inválido (campo: num_cpf)"}
```

Sem esse handler, o frontend recebia JSON bruto ilegível.

### Banco — unique constraint em `num_cpf`

```sql
DROP INDEX idx_pac_cpf;
ALTER TABLE pacientes ADD CONSTRAINT uq_pac_cpf UNIQUE (num_cpf);
```

Equivalente no model: `UniqueConstraint("num_cpf", name="uq_pac_cpf")`.

### Frontend — `Recepcao.jsx`

Função `validar()` atualizada:
- `dtnasc` agora é **obrigatória** (antes só validava se preenchida)
- Valida data real, não futura, não absurda
- Estado `erroDtnasc` com borda vermelha + mensagem inline no campo DN
- Erro chega ao usuário via `data.detail || data.message` (antes só `data.detail`)

## 5. Correção — número de registro persiste entre telas

### Problema

O `App.jsx` usa renderização condicional (`tela === "recepcao" ? <Recepcao> : <Historico>`), então navegar para o Histórico **desmonta** o componente `Recepcao`. Os `useRef` (`ultimoRegistroRef`, `ultimoTurnoRef`) são resetados para `null` na remontagem, fazendo o registro voltar a `01`.

### Solução

Persistência via `localStorage`:

- `handleAtendimento` → salva `ultimo_registro` e `ultimo_turno` após sucesso
- `handleLimpar` → salva antes de chamar `sugerirAtdInfo`
- `useEffect` inicial → lê do localStorage ao montar (sobrevive navegação e F5)

## 6. Correção — botão Família

### Problema

1. O localStorage era sobrescrito com endereço vazio quando o paciente carregado não tinha endereço (maioria dos migrados após limpeza de PRINCIPAL/CENTRO)
2. `handleFamilia` usava `logpcn || prev.logpcn` como fallback — quando o salvo era `""`, devolvia o valor antigo da tela

### Solução

```javascript
// Só atualiza localStorage se o paciente tem endereço preenchido
if (dados.logpcn || dados.numpcn || dados.bairro_pcnte) {
  localStorage.setItem("ultimo_endereco", JSON.stringify({ ... }));
}

// Cola o endereço diretamente, sem fallback
setForm(prev => ({ ...prev, logpcn, numpcn, bairro_pcnte }));
```
